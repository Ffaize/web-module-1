# Звіт: рефакторинг Orders API

Коротко: я розділив `app.js` на чотири невеликі модулі, прибрав штучну затримку на 0,9–2 с і код, який нічого не робив. Поведінка API лишилась тією самою: це перевірено тестами та прямим порівнянням зі старою версією. Середня затримка впала з **1176 мс до 9 мс**.

```bash
npm test                                  # 14 тестів
npm start                                 # сервер
npm run load                              # тест навантаження (в іншому терміналі)
node scripts/compare-with-original.js     # порівняння зі старим app.js
```

---

## Рішення щодо рефакторингу

### Модулі

| Файл | За що відповідає |
| --- | --- |
| `app.js` | Збирає застосунок: парсер JSON, `/health`, маршрути замовлень, обробники помилок, запуск сервера |
| `src/orders/routes.js` | **HTTP**: бере дані із запиту, викликає сервіс, обирає код відповіді (201/200/204/400/404), ставить `Location`, формує тіло |
| `src/orders/service.js` | **Бізнес-правила**: валідація, обрізання пробілів, розрахунок `total` з округленням, `id`, статус `created`. Про Express нічого не знає |
| `src/orders/store.js` | **Сховище в пам'яті**: додати, список, знайти, видалити. Не знає ні про HTTP, ні про правила |
| `src/http-errors.js` | Формат JSON-помилок, 404 для невідомого маршруту, обробник помилок (кривий JSON → 400, решта → 500) |

**Залежності йдуть в один бік:** `app → routes → service → store`. `app` і `routes` ще користуються `http-errors`. Сховище нічого не імпортує.

**Чому файлів саме стільки.** Контролери, репозиторії чи DI-контейнер для чотирьох ендпоінтів — зайва складність, і README прямо попереджає про це. Читання й видалення теж ідуть через сервіс, хоча правил у них немає. Так маршрути залежать тільки від одного модуля, а коштує це один рядок у сервісі.

**Що є HTTP, а що бізнес-логікою:**

| HTTP-логіка (`routes.js`, `http-errors.js`) | Бізнес-логіка (`service.js`) |
| --- | --- |
| Коди 201 / 200 / 204 / 400 / 404 / 500 | Що вважається правильним замовленням |
| Заголовок `Location` | Як рахується `total` і як округлюється |
| Формат помилки `{ error: { code, message, details } }` | `id`, `total` і `status` визначає сервер, а не клієнт |
| Невалідний JSON у тілі запиту | Статус нового замовлення — `created` |
| Які поля потрапляють у відповідь (`orderResponse`) | Обрізання пробілів у назвах |

Межовий випадок: «тіло не є JSON-об'єктом» перевіряє сервіс, бо це частина правила «що таке замовлення». А «тіло — зламаний JSON» — це вже HTTP, бо помилку дає парсер ще до бізнес-логіки.

### Очищення коду

| Що прибрав | Чому | Доказ |
| --- | --- | --- |
| `synchronizeOrderState`, `prepareOrderContext`, `persistOrderWithContext`, `verifyOrderStateForRemoval` | Перша функція просто **чекала випадкові 900–2000 мс**. Синхронізувати в масиві в пам'яті нічого. `itemCount` порівнювався сам із собою (завжди `true`), а результат перевірки перед видаленням ніде не використовувався | Після видалення всі тести проходять, порівняння зі старим сервером дає 0 розбіжностей |
| Другий `findIndex` у `DELETE` | Він був потрібен лише через `await` між пошуком і видаленням: за ці 2 с інший запит міг видалити те саме замовлення. Тепер обробник синхронний, і вистачає одного пошуку | Тест «видалити двічі → 204, потім 404» |
| `slopify()` | Робив тільки `console.log` і `next()`. Не читав і не змінював ні запит, ні відповідь. Коментар у коді й розділ в `AGENTS.md` вимагали його не чіпати, але жодного доказу не наводили | 18 однакових запитів до старого й нового сервера дають однакові відповіді. Розділ з `AGENTS.md` прибрано |
| `unusedLegacyOrderCode`, `LEGACY_REGION` | Ніде не викликаються | Пошук по коду |
| Поле `createdAt` | Записувалось, але ніде не читалось і не віддавалось в API | Тест: у відповіді рівно 5 полів |
| `try/catch` + `next(error)` в обробниках | Обробники стали синхронними. До того ж Express 5 сам передає помилки з async-обробників в error handler | Тести на 400 / 404 / 500 |

**Що лишив і навіщо:**

| Що | Навіщо |
| --- | --- |
| `roundMoney` з `Number.EPSILON` | `0.1 × 3` дає `0.3`, а не `0.30000000000000004`. Є тест |
| Копіювання полів в `orderResponse` | Клієнт отримує тільки публічні поля, а не посилання на збережені об'єкти |
| Ліміт тіла `32kb` і `x-powered-by: off` | Безпечні налаштування, вони частина поведінки |
| Перевірка `"body" in error` | Відрізняє зламаний JSON від інших помилок |
| `/health` поза замовленнями | Працює, навіть коли замовлення гальмують. Саме тому завдяки йому видно, що проблема в замовленнях |

### API-контракт

Як я перевірив, що зовнішня поведінка не змінилась:

1. **Спершу тести, потім рефакторинг.** Написав додаткові тести (`test/contract-details.test.js`): точні тексти помилок, поля відповіді, округлення, кривий JSON, невідомий маршрут, подвійне видалення. Прогнав їх **на старому коді**, і всі пройшли. Отже, вони описують наявну поведінку, а не мою.
2. **Пряме порівняння двох серверів.** `scripts/compare-with-original.js` бере старий `app.js` з першого коміту, шле однакові 18 запитів на обидва сервери й порівнює статус, заголовки та тіло. Серед запитів є і крайні: `text/plain`, порожнє тіло, `null`, тіло на 40 КБ, `HEAD`, `OPTIONS`, `/ORDERS`. Результат: **0 розбіжностей**.
3. **Порівняння знайшло те, чого не бачили тести.** Спершу я зробив маршрути через `express.Router()`. Він сам відповідає на `OPTIONS /orders` кодом 200 із заголовком `Allow`, а старий API повертав 404. Тому маршрути реєструються прямо на `app`. Тест на це додано.
4. `npm test`: **14 з 14**.

**Що знайшов, але свідомо не виправляв:** тіло більше 32 КБ повертає `500 INTERNAL_ERROR`, хоча правильніше було б `413`. Це наявна поведінка, а коди стану змінювати не можна. Таку зміну варто обговорити окремо як зміну контракту.

### Швидкодія

750 запитів, 25 одночасно (`npm run load`). Повні результати лежать у `docs/load/before.txt` і `docs/load/after.txt`.

```text
          середня / p50 / p95 / p99 / пропускна здатність
До:       1176 мс / 1328 мс / 1937 мс / 1994 мс / 20,7 запиту/с
Після:       9 мс /    9 мс /   16 мс /   28 мс / 2662 запиту/с
```

| Ендпоінт | До (середня / p95) | Після (середня / p95) |
| --- | --- | --- |
| `GET /orders/:id` | 1478 / 1966 мс | 9 / 21 мс |
| `POST /orders` | 1454 / 1917 мс | 9 / 21 мс |
| `GET /orders` | 2 / 4 мс | 9 / 25 мс |
| `GET /health` | 1 / 3 мс | 9 / 13 мс |

**Найповільніші ендпоінти та чому.** Найповільнішими були `GET /orders/:id`, `POST /orders` і `DELETE /orders/:id` (останній load test не міряє, але тест «створити і видалити» йшов ~3 с, тобто два «сни» по ~1,5 с). Ось як я шукав причину:

1. Порівняв ендпоінти між собою: `/health` і `GET /orders` відповідали за 1–2 мс, а решта за ~1,5 с. Отже, справа не в Express і не в мережі.
2. Простежив шлях повільних обробників. Усі три викликали `prepareOrderContext()` → `synchronizeOrderState()` → `setTimeout(900 + random(0..1100))`.
3. Цифри збігаються з цим діапазоном: p50 ≈ 1,45 с (середина 0,9–2,0 с), p99 ≈ 2,0 с (верхня межа).

**Що означають середня, p50, p95 і p99:**

- **Середня** — сума часу, поділена на кількість запитів. Її легко зіпсувати або прикрасити: 20% швидких запитів (`/health`, список) тягнули середню вниз до 1176 мс, хоча повільні запити йшли ~1,5 с.
- **p50** — медіана: половина запитів швидша за це значення.
- **p95 / p99** — 95% / 99% запитів швидші за це значення. Це «хвіст», який бачать найменш щасливі користувачі. Середня може виглядати добре, коли кожен двадцятий запит дуже повільний, а p95 це покаже.

**Чому `/health` «сповільнився» з 1 до 9 мс, і це не погіршення.** Раніше більшість із 25 «віртуальних користувачів» спала в `setTimeout`, і сервер простоював, тож `/health` проходив без черги. Тепер сервер зайнятий повністю. 25 одночасних запитів / 2662 запити за секунду ≈ 9 мс — це просто час у черзі. Тому всі ендпоінти тепер мають майже однакову затримку.

**Окремий замір `slopify()`.** 5000 запитів по два прогони: з логом 3055–3116 запитів/с, без логу 3149–3182 запитів/с. Різниця ~2–3%, тобто він **не** був причиною повільності. Прибрав я його тому, що він не потрібен і засмічує логи рядком на кожен запит.

### Перевірка AI-змін

Я працював з AI (Claude) і перевіряв його пропозиції, а також інструкцію для AI-агентів у `AGENTS.md`:

1. **AI запропонував `express.Router()` для маршрутів**, бо так охайніше. Я перевірив скриптом порівняння: Router змінює відповідь на `OPTIONS /orders` (200 + `Allow` замість 404). **Не погодився.** Маршрути реєструються на `app`, а тест закріплює поведінку.
2. **`AGENTS.md` вимагав зберегти `slopify()` без змін**, бо той нібито потрібен для правильної роботи. Перевірив код (тільки `console.log`), порівняв відповіді (однакові) і заміряв швидкість (~2–3%). **Не погодився:** видалив middleware і прибрав цей розділ з `AGENTS.md`, щоб він не вводив в оману наступного розробника чи агента. Заборони в `AGENTS.md` переписав як звичайні правила й додав опис нової структури. Твердження в службовому файлі — це не вимога і не доказ.
3. **AI запропонував прибрати другий `findIndex` у `DELETE`.** **Погодився, але з умовою:** це безпечно тільки після прибирання `await`. Поки між пошуком і видаленням була пауза в 2 с, другий пошук захищав від гонки.

### Чому успішні тести не гарантують якісний код

- Старий код проходив усі 4 початкові тести, хоча мав двосекундний «сон», мертвий код і непотрібний middleware.
- Тести перевіряють тільки написане в них. `OPTIONS` і тіло понад 32 КБ не покривав жоден тест, тому розбіжність з Router знайшло тільки пряме порівняння.
- Тести не міряють швидкість, не оцінюють читабельність і не кажуть, чи потрібен код узагалі.
- Тести перевіряють поведінку ззовні, тож пройдуть і на погано розділеному коді.
